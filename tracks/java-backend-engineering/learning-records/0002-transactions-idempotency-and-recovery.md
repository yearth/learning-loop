# 记录 0002：事务、幂等与失败恢复

日期：2026-09-08。形式：基于通用下单场景的教学问答；本轮未验证真实项目链路，也未进行编码或运行实验。

## 已在问答中独立表达

- 仅凭方法调用形式，不能判断是否跨进程；Web 层通过 RPC 委托业务只能作为待验证假设。
- 上游超时不代表下游停止，未结束的工作可能持续占用资源。调用超时时，业务结果可能未知，不能直接认定失败。
- 查询失败不能当成订单不存在；下单重试应复用同一次操作的标识。
- 刷新后应查询服务端状态；进程重启会丢失仅保存在内存中的待办。
- 订单与库存修改应一起成功或回滚；数据库事务已提交后，Web 层超时不会自动撤销提交。
- 最后一次简短检索正确区分了两项职责：持久化用于恢复待办，幂等用于避免重复补偿效果。尚未独立展开实现细节。

## 经讲解修正，待独立复述

- 查询成功但未查到订单，也不能证明原请求之后不会提交；查询与重试之间存在并发窗口。
- 请求标识应在首次发送前确定并可恢复；订单编号可能随响应丢失，不能作为唯一恢复依据。新的购买意图使用新标识，同次重试复用旧标识。
- 防重复操作与防超卖的区别不在用户是否相同：唯一操作标识防重，库存条件更新和数据库并发控制保护库存；业务仍需检查更新结果。
- SQL 更新零行可能是正常执行但未满足业务条件，需要业务代码触发失败处理。
- 普通本地事务不自动覆盖远端服务已提交的数据库事务。跨服务失败需要额外协调，例如补偿或预留与确认。
- 补偿请求再次送达不意味着库存必须再次增加。库存侧将补偿唯一记录与库存变更放在同一个本地事务中，才能避免二者分离造成的崩溃窗口。
- 协调方持久化待办并恢复处理，执行方保证补偿幂等；协调方状态暂时落后时，可通过查询或安全重试收敛。
- 待补偿记录若属于已回滚的订单事务，也会消失；提前持久化操作进度的完整恢复设计尚未展开。
