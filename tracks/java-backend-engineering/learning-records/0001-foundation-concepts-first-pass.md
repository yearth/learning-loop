# 记录 0001：基座概念第一遍 —— 注解、边缘鉴权、RPC、故障分类

通过三轮教学问答 + 两轮检索复述建立的概念基座，全部达到"能自我解释"标准：

- **注解机制**：注解是编译进 class 文件元数据的纯标签，自身无逻辑；消费者分三类 —— 编译器（`@Override`）、注解处理器（Lombok 类）、运行时框架（Spring 反射）；保留级别 SOURCE / CLASS / RUNTIME。与 TS 装饰器的本质区别：装饰器是被立即执行的函数，注解是被机器读取的数据。（纠正：无消费者的注解完全惰性、编译照常通过；不等同于注释 —— 注释不进产物，RUNTIME 注解会进。）
- **执行模型**：拦截器（机器）先于 Controller 方法执行，注解永不执行、只被反射读取；两者可同时来自共享库、运行在同一 web 进程内。理解一个注解 = 找到它的消费者（沿 import 追到依赖 jar，必要时用 `javap` 看字节码）。
- **边缘鉴权架构**：校验机器以共享库拦截器形态运行在业务进程内；"你是谁"的判定经 RPC 委托给远端统一鉴权服务。鉴权失败出口两种形态：302 跳转 / 直接写 JSON 错误体 —— 两者都是合法 HTTP 响应。
- **故障分类**：传输失败（连接不上 / 等到超时也无响应）vs 业务失败（响应合法但内容为错）；同一次失败在调用方与服务端的分类可以不同（网关超时：调用方视角是传输失败，服务端视角是孤儿工作仍在执行）。
- **孤儿请求与超时预算**：调用方超时不取消下游工作，在途工作继续占用线程 / DB 连接 / 内存；并发数 = 到达速率 × 平均处理时长（Little's Law）；持续变慢 + 预算错配 → 资源枯竭 → 雪崩（原本能成功的请求陪葬），重试与用户刷新是放大器。正确预算：每跳超时 > 下游所有跳之和，让最内层先超时、错误快速上冒。
- **RPC 三层关系**：RPC 是调用模式，Thrift / gRPC 是实现该模式的框架，各自定义线上协议；IDL 是中立契约、编译生成双端代码；pom ↔ package.json（Maven/npm、`~/.m2`/`node_modules`、私服/registry、多模块/workspace）。

**含义**：L1 单链路追踪的概念铺垫已齐（注解、鉴权、RPC、故障分类无需再讲）；熔断 / 限流 / 重试仅名词级认知，留 L3 展开；下一课从授权前端仓库的真实页面发起，走"预测 → 追踪 → 反向分类"流程。

**Evidence**：2026-09-07 教学问答三轮 + 检索复述两轮（孤儿请求、超时预算因果链复述通过）。对照一个授权企业级 Java 仓库只读验证（仓库 / 类名 / 坐标按公开纪律隐去）：web 层无数据访问代码、经生成的 RPC stub 出口（包扫描 + 构建依赖确认）；鉴权拦截器位于共享库、经 RPC 调统一鉴权服务（import 链追踪 + `javap` 字节码确认）；鉴权失败出口形态（字节码确认）。未知项：网关层粗粒度鉴权是否存在（需部署拓扑确认）；实际超时预算值（部署文件未含，推断在配置中心）。
