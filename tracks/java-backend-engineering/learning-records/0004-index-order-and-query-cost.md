# 记录 0004：索引排列与查询成本

学习阶段：记录 0003 提交后至 2026-09-16。形式为通用示例讲解、排列推演与问答；未执行建索引、数据库实验或性能测试。

## 已在问答中表达

- 修改索引字段，需要同步维护索引对应关系；不修改相关字段时，该对应关系不变。具体维护步骤经讲解补齐。
- 对于“企业、申请人、时间”的联合索引，先按企业排列，再按申请人排列，最后按时间排列。因此一个企业当天的记录可能分散在不同申请人下面。
- 对“所有企业某一天的记录”这一排列问题，能够选择日期在前的索引，使目标记录集中在一个时间范围。
- 主动将索引概括为“空间换时间”，并指出小表直接扫描可能比走索引更快。写入维护成本、回表和命中比例经讲解补充。

## 已纠正，仍需独立验证

- 最初将“申请人、时间”索引中所有人当天的记录判断为集中；经展开数据排列后，能够迁移到三列索引场景。
- 最初认为 WHERE 中 AND 条件的书写顺序会决定先筛选哪个字段；已讲解索引列顺序、SQL 表达顺序和实际执行计划的区别，尚未独立复述。
- 索引第一列是企业，不意味着每次查询都必须先取出企业全部数据。组合条件可以直接定位；是否选择该索引由优化器决定。
- 缺少中间列条件，不等于索引完全无用；仍可能利用前面的列缩小范围。实际访问路径需要执行计划验证。

## 已接触，尚未评估

- 普通索引允许重复值，辅助查找；唯一约束同时表达不允许重复的规则。
- 索引由数据库自动维护；树形结构可逐层缩小查找范围。尚未展开页结构、B+ 树细节或实际维护算法。
- 索引占用空间并增加相关写入的维护成本。是否加速取决于查询与数据分布，不能只凭“存在索引”判断。
- 在 InnoDB 场景中，经二级索引找到主键后再读取完整记录称为回表。需要大量回表时，扫描可能更划算；本轮只讲解概念，未验证执行成本。
