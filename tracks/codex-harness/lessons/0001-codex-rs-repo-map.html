鸟瞰：codex-rs 是一座什么形状的仓库

你听说"Codex harness 开源了"。这一课先搞清楚：开源出来的到底是什么形状的东西。

先猜再看 · 不要查这个开源仓库的 Rust workspace（codex-rs）里，大约有多少个 crate？

137 个（口径 2026-08 的 workspace members）。这个数字本身就是本课的核心知识点：开源出来的主体不是一小段"agent 循环"，而是一整套环绕模型的环境设施。下面我们会看这座城市的分区。

1 · 什么被开源了

先对齐事实，四个都可以点进原文核对：

  • 仓库是 openai/codex，Apache-2.0 协议，主体是 Rust workspace codex-rs。
  • Codex CLI、桌面 App（codex app）、IDE 扩展（VS Code 等）共用这一个内核——README 原话："Lightweight coding agent that runs in your terminal"，而 app-server 的 README 说它是 "the interface Codex uses to power rich interfaces such as the Codex VS Code extension"。
  • workspace 里有 137 个 crate（Cargo.toml members）。
  • 其中 core 是最大的一个 crate——大到仓库自己的 AGENTS.md 写着 "resist adding code to codex-core"。
一个 crate ≈ 一个独立编译的 Rust 包，可以粗略类比 npm 的一个 package。137 个 crate = 137 个有边界的模块。
最小的事实，最大的启示：你平时说的 "agent loop" 只是这座城市里的一个街区（core），而城市的大部分面积是别的。 —— 本课核心洞察

2 · 分层地图

把 137 个 crate 按职责切成三带（完整速查版在 reference/codex-rs-map，建议留着当索引）：

入口层 FRONTENDS —— 把某种界面接进内核

cli → codex 主命令 tui → 终端交互界面 exec → codex-exec 非交互 app-server → JSON-RPC（App / IDE 用） mcp-server → 暴露为 MCP server（原型）

内核层 KERNEL —— agent 的大脑

core（最大 crate：loop · thread · context · 工具编排） protocol（Op / EventMsg） tools apply-patch prompts

基础设施层 INFRASTRUCTURE —— 环绕大脑的器官

安全策略 ≈8：sandboxing · execpolicy · linux-sandbox · bwrap … 记忆状态 ≈6：rollout · thread-store · history … 模型接入 ≈9：model-provider-info · codex-api · ollama … 扩展生态 20+：skills · plugin · hooks · ext/* … 云端与 utils：cloud-tasks · 大量工具库
注意数量的分布：入口 6 个、内核不到 10 个、剩下 120 个左右都在基础设施和扩展生态。这就是"开源的主体是环境工程"的直观版本。

这正对应你已经熟悉的 harness engineering 判断：把模型当固定 worker，工程量全在环境上。OpenAI 自己的仓库结构就是这个论点的证据——loop 很小，环境很大。

3 · 一次任务的粗路径

你在终端敲一句"帮我修这个测试"，粗粒度上经过这几站（每站一句话，细节留给后面的课）：

  1. 入口：cli 启动，交互模式落到 tui，你的输入变成一个 Op（操作请求）。
  2. 词汇表：protocol crate 定义 Op 和 EventMsg——前后端之间只说这套话（protocol.rs 里两个大枚举）。
  3. 内核：core 接管：装配上下文（该给模型看什么）、发起推理请求。
  4. 工具执行：模型要跑命令/改文件 → tools 编排，sandboxing + execpolicy 决定"允不允许、怎么拦"，apply-patch 负责把模型输出落成文件改动。
  5. 结果回填：工具输出作为新的输入回到模型，循环直到任务完成。
  6. 事件外送：全程每一步都以 EventMsg 流回前端渲染；同时 rollout 把事件流落盘——这就是以后 resume 会话的底子。
第 2 课就钻进第 3、5 步之间的循环体。现在你只需要记住" vocabulary → brain → hands → feedback "这个骨架。

检索 3137 个 crate 里，数量占比最大的一类是？

内核不到 10 个、入口约 6 个，其余 120 个左右都是环境设施：安全、记忆、扩展、utils。harness 的本体是环境工程。

动手 5 分钟（可选但强烈建议）——亲手验证今天的事实。先进入 checkout 根目录，再跑三条命令（pwd 确认自己在 openai-codex 里）：

cd ~/agent-playground/repos/external/openai-codex

# 1. 数一数 crate 到底多少个
awk '/^members = \[/,/^\]/' codex-rs/Cargo.toml | grep -c '"'

# 2. 找到前后端的"词汇表"——两个大枚举
grep -n "pub enum Op\b\|pub enum EventMsg" codex-rs/protocol/src/protocol.rs

# 3. 看 app-server 的自我介绍
head -8 codex-rs/app-server/README.md

期望输出：137；两处带行号的枚举定义；README 第一段的 "power rich interfaces"。没有本地 checkout 的话，在 GitHub 上打开 Cargo.toml 数 members 也算。

本课一页纸

  • 开源的是整套 harness：137 个 crate，CLI / App / IDE 共用一个内核。
  • 三带结构：入口层（接界面）→ 内核层（core + protocol + tools，小而重）→ 基础设施层（安全 / 记忆 / 模型接入 / 扩展，大而散）。
  • 一次任务的骨架：词汇表 protocol（Op / EventMsg）→ 大脑 core → 双手（tools + sandboxing）→ 回流（EventMsg 给前端，rollout 落盘）。
